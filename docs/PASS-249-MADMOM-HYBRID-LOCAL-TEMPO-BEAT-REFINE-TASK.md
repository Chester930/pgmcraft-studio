# Pass 249 任務書：madmom hybrid 小節內部拍點改用「多樂器訊號聚類 +
局部節奏斜率」取代單一瞬態磁吸（`MicroTimingTransientSnapNode`）

**狀態**：設計已跟使用者討論確認過方向，可直接轉交 Codex CLI
執行。**這是全新機制，取代 Pass246/248 已經證實效果不明確的
「單一最大聲瞬態磁吸」，不是在它上面小修——`MicroTimingTransientSnapNode`
本體維持不動（Pass247留下的噪聲門檻改動繼續保留，它保護的是
legacy pipeline既有呼叫端，不受這次影響），只是`madmom_hybrid.py`
不再呼叫它。**

---

## 0. 背景：為什麼要換方向

Pass245（只查證）發現：前奏中後段（5.5-20.0秒）跟疑似藏在Chorus1
標籤裡的間奏段（100.5-106.0秒），madmom的降拍（第一拍）準確
（13-41毫秒），但小節內部第2、3、4拍被madmom的DBN模型拉成機械式
等分，跟golden顯示的真實表情性彈性節奏（同一批小節四拍間距起伏
近50%）對不上。

Pass246-248 試過「重用既有`MicroTimingTransientSnapNode`，對每一拍
在±35ms視窗內找鼓組波形最大聲瞬態、磁吸過去」：

- Pass247真實pipeline驗證：**核心目標沒達成**（前奏段套用前後
  幾乎持平29.8ms→28.3ms，Chorus1中段甚至略微變差18.2ms→19.9ms），
  而且發現**套用到降拍時會有退步風險**（附近有比真降拍更大聲的
  裝飾音/次要擊點時，會把已經準的降拍吸偏，1-2個小節從50ms內被
  推到54-72ms外）。
- Pass248把降拍排除在磁吸範圍外，安全疑慮解除（降拍100%維持
  準確），但小節內部效果依然不明確——**證實問題不在「有沒有套用
  到降拍」，是「單一最大聲瞬態磁吸」這個方法本身在這種稀疏證據
  段落不夠可靠**：稀疏段落裡最大聲的鄰近訊號常常不是真正的拍點，
  而是裝飾音/次要擊點；而且完全沒有訊號時只能維持死板等分，沒有
  更好的處理。

**使用者確認的新方向**：改用「多樂器訊號聚類 + 局部節奏斜率」，
兩層機制取代單一瞬態磁吸。

## 1. 新機制設計：`_estimate_local_tempo_beats`

在 `pgm_craft/workflow/madmom_hybrid.py` 新增一個獨立函式（不重用
`MicroTimingTransientSnapNode`，那個節點本體維持不動，`madmom_hybrid.py`
單純不再呼叫它），取代 `MadmomPrimarySegmentSpliceNode.execute()`
裡呼叫`MicroTimingTransientSnapNode`那整段（`beat_tracking_bt.py`
匯入也一併移除，除非後續發現還有其他地方需要）：

```python
def _estimate_local_tempo_beats(
    grid,                    # 目前的完整拍點網格（含降拍+內部拍）
    kick_anchors,
    snare_anchors,
    bass_anchors,
    cluster_tolerance_ratio=<待離線校準>,
    max_ramp_ratio=<待離線校準>,
):
    """對每個小節（相鄰兩個降拍之間）的第2、3、4拍，依序：

    1. 算這個小節自己的『名目等分拍長』q =（下一個降拍-這個降拍）/4。
    2. 名目位置 p_k = 這個降拍 + k*q（k=1,2,3）附近，在
       ±(cluster_tolerance_ratio * q) 範圍內，合併搜尋
       kick_anchors ∪ snare_anchors ∪ bass_anchors 三個既有陣列
       （這些都是pipeline更早階段已經算好的真實onset時間，不用
       重新做偵測、不需要額外載入音檔）。
    3. 如果範圍內找到 >=1 個候選：取這些候選的『中位數』（不是
       單一最大聲峰值）當新位置——用中位數而不是加權平均/最大值，
       是因為多個樂器的候選可能本來就有自然的微小時間差，中位數
       對單一離群值更穩健。
    4. 如果範圍內完全沒有候選：不要死板等分，改用『局部節奏斜率』
       柔性偏移——分別用『這個小節自己的q』、『前一個小節的q_prev』、
       『後一個小節的q_next』（前後小節都是已經準確的降拍算出來的，
       不是猜的），算一個有界的線性斜率調整（讓小節內部第1-4份拍長
       從『偏向q_prev』平滑過渡到『偏向q_next』，但四份拍長總和仍然
       精確等於這個小節真正的降拍間距，不會累積偏移），斜率幅度
       用 max_ramp_ratio 限制上限（避免鄰近小節剛好有雜訊造成的
       極端速度差被誇大套用）。首尾小節缺少前一個/後一個小節時，
       退回這個小節自己的q（等同純等分，不會出錯）。
    """
```

**明確要求**：降拍（第1拍）完全不在這個函式的處理範圍內——這個函式
只接收/回傳每個小節的3個內部拍位置，降拍時間由既有的弱區段拼接/
尾聲外推邏輯決定，維持Pass248已經驗證過的「降拍絕對不動」保證，
不需要重新驗證這件事（純邏輯保證，不是機率性的）。

## 2. 參數需要離線校準，不能憑感覺寫死

`cluster_tolerance_ratio`（訊號搜尋窗佔小節拍長的比例）跟
`max_ramp_ratio`（沒有訊號時，節奏斜率調整的上限比例）**都需要用
真實資料校準**，比照Pass236/242當初的校準方法：

1. 用這首歌真實的madmom降拍網格 + 真實的`kick_anchors`/
   `snare_anchors`/`bass_anchors`（需要透過一次execute()層級的
   埋點從真實pipeline擷取，比照Pass222/241已經用過的安全埋點手法
   ——只monkeypatch單一節點的execute()、finally裡還原，不要用
   Pass206/207踩過的全域`__init__`monkeypatch），對Pass245標出的
   兩段（5.5-20.0秒、100.5-106.0秒）逐點跟golden的真實beat 2/3/4
   時間比對，掃描幾組候選參數（例如`cluster_tolerance_ratio`
   0.15/0.20/0.25/0.30，`max_ramp_ratio`0.10/0.15/0.20），選一組
   讓這兩段的beat-level平均誤差**確實改善**（不是持平也不是變差）
   的參數。
2. **如果掃完所有合理範圍的參數組合，這兩段的beat-level誤差依然
   沒有辦法比Pass248（無作為）明顯更好**——誠實回報這個結果，不要
   為了呈現「這次成功了」硬選一組看起來沒變差、但也沒真的變好的
   參數，寫進`docs/BT-BUILD-PROGRESS.md`老實記錄，跟Pass246/247/248
   一樣的誠實揭露標準。這是探索性的新方向，不保證一定有效，任務書
   要求的是「認真試過、如實回報」，不是「一定要生出一個成功案例」。

## 4. 驗證流程

### 4.1 離線驗證（先做）

1. 合成案例：構造一個小節，內部第2拍附近有kick+bass都同意的候選
   （中位數應該落在合理範圍內）；另一個小節完全沒有候選但前後
   小節有一致的漸慢趨勢（確認斜率調整方向正確、且被max_ramp_ratio
   限制住不會過頭）；再一個小節前後小節速度相同（確認退化成純
   等分，不會無中生有製造抖動）。
2. 用第2節的埋點方法拿到這首歌真實的三個anchor陣列，跑第2節描述
   的參數校準掃描，記錄完整結果（比照`scratch/pass236_offline_calibration.json`
   的做法留存一份校準紀錄）。

### 4.2 真實資料驗證（離線驗證選定參數後才做）

1. **安全底線（最重要，但這次不用重跑真實pipeline才能確認）**：
   降拍完全不受這個函式影響是程式碼結構保證的（函式簽章只接收/
   回傳內部拍位置），寫一條測試直接斷言「呼叫這個函式前後，降拍
   陣列完全不變」即可，不需要為了這個特定主張再花一次動輒
   9-60分鐘的真實pipeline。
2. **真的要驗證效果，才需要真實pipeline**：跑一次完整pipeline
   （`madmom_hybrid_approved=True`），逐拍（不只降拍）比對golden，
   針對Pass245標出的兩段報告清楚的「有改善/持平/變差」結論，
   附上具體數字，不要模糊帶過。
3. 確認其餘段落（Intro/Verse1/Chorus1其他部分、Outro）沒有意外
   退步——這個函式理論上只影響小節內部拍點，不該碰到降拍層級的
   分數，但仍要跑一次確認，不能只憑理論推斷就跳過。
