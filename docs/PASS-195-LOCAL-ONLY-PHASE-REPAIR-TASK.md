## 0. 背景

使用者對 Pass 194 的結果表達疑慮：「我感覺近期的一些修改，並沒有優化
反而變得更差」。直接比對數字證實了這個直覺：

| 版本 | 小節數（差黃金 121） | 不規則小節數 |
|---|---|---|
| Pass 183（Pass 184+ 這整輪修改開始前的基準） | 117（-4） | **1** |
| Pass 194（Pass 193 修正保護區段之後） | 114（-7） | **10** |

Pass 183 基準的「1 個不規則小節」只是曲末收尾，正常現象；它真正的問題是
**相位錯誤**（18-20 秒的重音位置錯了快一拍——這正是整輪修改要解決的
真實聽感問題），不是小節拍數異常。

Pass 194 修好了相位，但代價是多出 9 個新的不規則小節。追查發現（見
`scratch/diagnose_pass194_irregulars.py`）：這 9 個位置裡只有 3-4 個
靠近保護區段邊界，其餘 5-6 個（例如 measure 6/53/55/72/101）完全跟保護
機制無關。直接比對 Pass 183 基準在同一時間段的資料，發現一個關鍵事實：
**底層拍點時間戳完全相同，只是標號的相位不一樣**。例如 77.8 秒附近：

- Pass 183（正確）：`76.737→1, 77.096→2, 77.45→3, 77.803→4, 78.18→1, ...`
- Pass 194（錯位）：`77.803→1, 78.18→2, 78.542→3, 78.889→4, 79.266→5, 79.672→6`

同樣的拍點，Pass 194 把「第 1 拍」標記錯位了一格。原因是：
`_ensure_44_phase_continuity`（Pass 193 引入、Pass 194 只是讓它尊重保護
區段）是「從一個錨點開始，機械式數 1-2-3-4 一路數到底」——只要曲子中間
任何一處跟 BeatNet / KickBassDownbeatVerifierNode / DownbeatRefineNode
等上游節點原本已經正確判斷的重音位置對不上（不需要靠近保護區段，只要
中途有任何一點原本的相位選擇跟機械式計數不同），這個機械式數法就會
悄悄跟真實重音錯開、一路數到下一個錨點才重新對齊，沿路冒出一堆本來不
存在的 5、6 拍怪異小節。**這不只是蓋掉了 SteadyPercussionCountAnchorNode
的保護區段，而是蓋掉了整條 Stage 3 拍點追蹤鏈在保護區段以外辛苦建立的
重音判斷**，改用一個從單一起點硬數到底的簡化邏輯取代。

## 1. 修法：只修「真的偵測到不規則」的區段

重寫 `_ensure_44_phase_continuity`：

1. 先找出既有的所有 downbeat（`beat==1`）位置，不分是否在保護區段內——
   這些都是上游整條 Stage 3 拍點鏈已經做出的判斷，預設信任。
2. 只有當相鄰兩個既有 downbeat 之間的拍數**不是** `beats_per_bar` 的
   整數倍，或雖然是整數倍、但內部應該存在的中繼 downbeat 卻沒有被標記
   （代表中間漏掉了一個重音標籤），才對這一小段做局部 1-2-3-4 補全——
   只影響這一小段本身，不會往前後任何方向擴散、不會「一路數到下一個
   錨點」。
3. 已經乾淨、既有 downbeat 間距本來就正確的區段完全不碰，維持上游原本
   的判斷（不管是不是在保護區段內）。
4. 保護區段內的標號永遠不被觸碰，即使剛好落在需要局部修復的區段裡。

```python
downbeat_idx = [i for i, r in enumerate(beat_rows) if r.get("beat") == 1]
for k, start in enumerate(downbeat_idx):
    end = downbeat_idx[k + 1] if k + 1 < len(downbeat_idx) else n
    span = end - start
    needs_repair = span % beats_per_bar != 0
    if not needs_repair and span > beats_per_bar:
        for sub in range(beats_per_bar, span, beats_per_bar):
            if int(beat_rows[start + sub]["beat"]) != 1:
                needs_repair = True
                break
    if not needs_repair:
        continue
    for offset in range(span):
        i = start + offset
        if _is_protected(float(beat_rows[i]["time"])):
            continue
        beat_rows[i]["beat"] = (offset % beats_per_bar) + 1
```

這個設計同時解決兩類問題：真的漏標 downbeat 的區段（局部補全）、以及
保護區段邊界造成的相位跳躍（同一套機制自然涵蓋，不需要額外程式碼）——
而且完全不會去動任何本來就正確、間距已經是 4 的倍數的區段。

## 4. 實作結果

### 4.1 修改內容與單元測試

`_ensure_44_phase_continuity` 改為只局部修復真的不規則的區段（見第 1
節）。新增/修正的單元測試（`test_sdd_pass193/194/188.py`、
`test_bt_workflow.py`）共 33 項全數通過，確認：保護區段內標號永遠不被
觸碰、空隙依然平滑補全、多個獨立保護區段互不干擾、沒有保護區段時退回
Pass 193 行為（向後相容）、真實 18-20 秒案例回歸、以及 Pass 188 原始
「保留合理短小節、防膨脹保護」設計恢復正確運作。這次修法本身架構上是
正確、必要的（修正了 Pass 193/194 整曲機械式覆蓋合理上游判斷的問題），
予以保留。

### 4.2 真實資料量化驗證：數字沒有改善

重跑 `scratch/run_pass195_default_pipeline_reverify.py`：114 小節
（差 -7）、不規則小節 **11**（比 Pass 194 的 10 還多一個）。Pass 194
的 9 個問題點（8.041s/21.458s/32.382s/77.803s/81.446s/93.802s/97.197s/
108.652s/152.023s）**全部依然不規則，一個都沒修好**。18-20 秒目標區段
本身依然正確（beat-1 在 18.568s/20.011s）。

### 4.3 追查：問題不在 `_ensure_44_phase_continuity`

在 `MeasureMapNode.execute()` 暫時插入除錯輸出，直接把 `beats`（進入
`build_measure_map` 之前的原始拍點陣列，尚未經過任何相位修復）存成
`outputs/pass195_raw_beats_debug.json`，重跑一次確認。以 77.803s 附近
為例，**原始輸入本身**就是：

```
76.367→1, 76.737→2, 77.096→3, 77.45→4,
77.803→1, 78.18→2,
78.542→1, 78.889→2, 79.266→3, 79.672→4,
80.02→1, ...
```

77.803 和 78.542 這兩個位置**都**被標成 `beat==1`——這是上游 Stage 3
拍點鏈（SteadyPercussionCountAnchorNode 等）自己的判斷，只間隔 2 拍
（不是保護區段邊界問題，兩者都在同一個保護區段 `[76.36, 78.52]` /
`[78.52, 82.16]` 的交界附近，但問題不是交界本身）。

核對 `_ensure_44_phase_continuity`（Pass 195 新邏輯）在這段的行為：
`77.803→78.542` 這個 2 拍span（`2 % 4 != 0`）觸發局部修復，但兩個位置
都在保護區段內，修復迴圈整段跳過、標號不變；`78.542→80.02` 這個 4 拍
span（`4 % 4 == 0`）判定為「已經乾淨」，完全不觸碰。也就是說，**這次
修法完全沒有動這段的任何標號**，78.542 應該仍然是 `beat==1`。

但最終輸出的 measure 53 卻是 `[(1,77.803),(2,78.18),(3,78.542),
(4,78.889),(5,79.266),(6,79.672)]`——78.542 變成了 `3`，不是 `1`！

追查 `_build_from_downbeats`（`_ensure_44_phase_continuity` 之後才執行）
發現真正原因：

1. `_measure_entry()` 建立每個小節的 `beats` 清單時，**完全不讀取原始
   標號**，只用小節內的陣列位置重新編號（`{"beat": index + 1, ...}`）。
   也就是說，最終顯示的 1-2-3-4-5-6 是「這個小節內第幾拍」，不是拍點
   陣列裡真正儲存的標號值——`_ensure_44_phase_continuity` 這整條線索
   （Pass 193-195）能控制的只有「哪些位置被當成小節分界」，管不到最終
   顯示的編號本身。
2. 真正決定「哪些位置被當成小節分界」的，是 `_prune_ghost_downbeats`
   （**Pass 170** 就存在的機制，比這整輪 Pass 181-195 的工作都早）：
   ```python
   common_step = statistics.median(gaps)   # 通常是 4（大部分小節 4 拍）
   ghost_threshold = 0.6 * common_step     # 通常是 2.4
   # 相鄰 downbeat 間距（陣列位置差）< threshold 就視為 ghost，剔除後一個
   ```
   77.803 到 78.542 只間隔 **2** 個位置，小於門檻 2.4，被判定為 ghost
   downbeat，**直接剔除**——78.542 這個真實存在、標號為 1 的拍點，就這樣
   在 `_build_from_downbeats` 內部被合併回上一個小節，變成該小節的
   「第 3 拍」。

**結論：這 9 個問題點的根因是 `_prune_ghost_downbeats` 把兩個間隔只有
2 拍的合法 downbeat 候選，其中一個當成「重複的 ghost」剔除掉了**——跟
`_ensure_44_phase_continuity`（Pass 193-195 這整條修改線）完全無關。這
也解釋了為什麼 Pass 194→195（改變 `_ensure_44_phase_continuity` 的行為）
對這 9 個位置的數字完全沒有影響：不管相位補全邏輯把標號改成什麼，只要
兩個 downbeat 間距在陣列位置上小於 2.4，`_prune_ghost_downbeats` 都會
把後面那個吃掉。

## 5. 後續：`_prune_ghost_downbeats` 是否還是正確的設計（未修復，待討論）

`_prune_ghost_downbeats` 是 Pass 170 時代的心臟保護機制，當時的假設是
「兩個離得很近的 downbeat 幾乎一定是同一個真實重音被偵測兩次的雜訊」。
但 Pass 181-191 大幅強化了 Stage 3 的 downbeat 判斷能力（多重獨立驗證
節點、局部 onset 偵測、半拍型態支援……），現在近距離出現兩個 downbeat
候選，未必再是雜訊——可能是真實的鼓點過門、切分音、或兩個不同驗證節點
各自基於證據做出的合理但密集的判斷。`ghost_threshold = 0.6 * common_
step`（间距小於 2.4 拍就剔除）這個門檻是否還適用，需要重新評估：

- 選項 A：調整/移除這個 pruning 機制，讓局部驗證交給下游（例如檢查
  「兩個 downbeat 之間的能量分布」而不是單純比較陣列間距）。
- 選項 B：保留 pruning，但改成不是「無條件剔除」，而是先判斷哪一個
  候選的證據更強（例如比對哪個更接近真實鼓點能量峰值），只剔除證據
  較弱的那個，而不是機械式「一律留前面那個」。
- 選項 C：找出這 9 個位置的 2 拍候選各自的來源證據，直接判斷哪個是對
  的、哪個真的是雜訊，再決定要不要動 pruning 邏輯本身。

這是一個需要重新設計、且會影響到 `_build_from_downbeats` 核心行為的
改動，範圍比這次的 Pass 195 大很多，因此本次任務書先如實記錄根因，
留給下一個任務（Pass 196？）決定要不要、以及怎麼處理。
