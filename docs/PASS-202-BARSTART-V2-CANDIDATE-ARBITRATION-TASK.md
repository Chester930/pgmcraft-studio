# Pass 202 任務書：幫 BarStart V2 的候選挑選加上多來源交叉驗證

**狀態**：缺口已在程式碼裡確認，設計方向明確（借用既有已驗證過的
`MeasureMapNode._reconcile_close_downbeats` 概念），可轉交 Codex CLI
執行。獨立於 Pass 200/201/203，可以並行或依序做。

---

## 0. 背景：已確認的缺口

使用者描述的 BarStart V2 概念是「每個分軌各自對照 v1 網格產生候選，
符合門檻的保留；當不同分軌的候選很接近但不完全一樣時，需要能驗證
哪一個才是對的」。查證程式碼確認：**前半段（各分軌產生候選）已經
實作，後半段（候選很接近時交叉驗證）完全沒有**。

`BarStartCandidateCommitNode._best_candidate`
（`pgm_craft/workflow/module3_barstart_v2_bt.py:1081`）：

```python
def _best_candidate(self, candidates: list[dict]) -> dict | None:
    if not candidates:
        return None
    return max(candidates, key=lambda item: (item["confidence"], -item["time"]))
```

直接選信心分數最高的候選，**不檢查候選之間是否有其他分軌的候選
在附近可以互相驗證，也不會因為「多個分軌剛好指向同一個位置」而
提高該位置的可信度**。例如鼓組候選 12.30 秒（信心 0.65）、和絃候選
12.45 秒（信心 0.60），系統直接選 12.30 秒，不會意識到「這兩個
這麼近，可能是同一個真實小節起點的兩種證據，該合併看待，而不是
二選一各自獨立比較」。

**這個系統裡已經有一個為了同一類問題（兩個候選太近、無法同時成立、
需要判斷誰對）而設計、且已經用真實資料驗證過的機制**：
`MeasureMapNode._reconcile_close_downbeats`（`pgm_craft/workflow/audio_nodes.py`，
Pass 197A）——用候選前後多個小節的全域相位一致性分數來仲裁，而不是
單一鄰居外推或單純比信心高低。但 BarStart V2 是完全獨立開發的
子系統，沒有借用這個概念。

---

## 1. 設計：兩層驗證機制

### 1.1 第一層：候選聚合（同一位置的多分軌共識，提高信心而非二選一）

在 `_normalize_candidates`（`:1046`）產生候選列表後、進入
`_best_candidate` 之前，新增一個聚合步驟：

1. 找出彼此時間差在一個小容差內（建議先用 50ms，這個系列已經反覆
   驗證過 50ms 是 onset 量化核對慣用的合理容差）的候選群組。
2. 同一群組內如果有 **≥2 個不同來源**（`evidence_sources` 不重疊）
   的候選，代表多個獨立分軌都指向這個位置——**這比單一分軌的高
   信心更可信**，應該合併成一個候選，信心分數用某種聚合方式提升
   （例如 `1 - product(1 - c_i)`，或更簡單的「取最高分再加一個
   共識加成」，具體公式需要用真實資料校準，不要憑空決定數字）。
3. 合併後的候選時間，建議取信心加權平均，而不是隨便選其中一個
   分軌的時間。

### 1.2 第二層：候選衝突仲裁（不同位置的候選互相矛盾時，才需要真的
「二選一」）

聚合完的候選裡，如果還有兩個以上的候選彼此時間差小於一個小節
（也就是不可能同時都是正確答案），才需要進入仲裁：

1. **不要重新發明一套仲裁邏輯**——直接參考（或視情況重用）
   `MeasureMapNode._reconcile_close_downbeats` 的一致性評分概念：
   對每個候選，計算它跟「前面已經確認的多個小節」用目前的拍距模型
   往前推算，有多少個吻合（而不是只看跟最近鄰居的距離）。
2. 這裡的「已經確認的小節」用 `committed_bar_starts`（已經 commit
   的小節），拍距模型用 `_expected_bar_duration`（`:1107`，已經存在，
   從 `v1_reference_beat_grid` 算穩健中位數）。
3. 仲裁後的決策要記錄可追溯理由（哪個候選贏、為什麼、一致性分數
   多少），寫進 `bar_start_decision_report`，比照這系列一貫的做法
   （`measure_map.json` 的 `phase_reconciliation` 欄位就是這樣做的）。

## 2. 安全機制

1. **這個修改不能改變「候選信心夠高才能 commit」這個基本規則**——
   聚合/仲裁只影響「多個候選之間怎麼選」，不能讓仲裁贏家繞過
   `default_threshold=0.7` 的門檻直接 commit。
2. **只在真的有多個候選互相矛盾時才觸發仲裁**——正常只有一個候選、
   或多個候選但彼此差距夠大（構成合理的不同小節）的情況，完全不
   受影響，這是這系列每個仲裁機制（Pass 197A、Pass 198A）都遵守的
   原則，仲裁邏輯不能誤傷正常情況。
3. **這個修法解決的是「選錯候選」的風險，不是「幾乎每小節都達不到
   0.7 門檻」的問題**——後者是 Pass 203 要診斷的獨立問題，不要期待
   這個修法能提升 commit 成功率，它只提升「commit 成功時選對答案」
   的機率。

## 3. 驗證計畫

1. **合成測試（第一層共識聚合）**：模擬鼓組跟貝斯候選在 50ms 內
   重疊、來源不同，驗證合併後信心分數比任一單獨分軌都高。
2. **合成測試（第二層仲裁）**：重現 Pass 197 任務書第 1 節示範過的
   真實案例模式（77.803s vs 78.542s 那種相距約 2 拍的衝突），驗證
   仲裁正確選出跟前面已確認小節序列一致性更高的候選。
3. **合成測試（沒有衝突時完全不受影響）**：只有一個候選、或候選
   彼此差距構成合理小節間距時，結果跟修改前完全一樣。
4. **既有測試全跑一次**：`tests/test_module3_bt.py` 全部要維持通過。
5. **真實資料驗證**：重跑 Pass 198/199 用過的真實回驗腳本，比對

   方法）。
